# CLAUDE.md

Read **[AGENTS.md](AGENTS.md)** first — it is the single source of truth for
this repository's architecture, commands, conventions and gotchas. This file
only adds notes specific to working here with Claude Code.

## Before you start

Run `flutter analyze` and `flutter test`. Both are expected to be clean
(109 tests, no analyzer issues). If they are not clean on a fresh checkout,
fix that before building anything on top.

## Things that look like bugs but are not

- `lib/data/content_version.dart` is generated by `tools/build_content.py`.
  Do not edit it, and do not "fix" its formatting.
- `assets/content/content.db` is a committed binary. It is generated, but it is
  committed on purpose so a release build never needs the original `.apkg`
  files, which live outside this repository.
- The scheduler takes `now` as a parameter everywhere instead of calling
  `DateTime.now()`. That is deliberate, not an oversight.
- `test/support/sqlite_test_setup.dart` contains Linux-specific library loading.
  It is required for the database tests to run at all; see AGENTS.md.

## When changing the scheduler

`lib/srs/sm2.dart` has no dependencies and 27 tests in `test/sm2_test.dart`.
Change behaviour there and the tests will tell you exactly what moved. Add a
test for any new rating or phase transition — the scheduler is the one part of
the app where a quiet mistake costs users weeks of mis-scheduled reviews.

## When changing deck content

Rebuild and re-run the tests in the same step:

```bash
python3 tools/build_content.py && flutter test
```

`test/app_database_test.dart` asserts against the real content (deck count,
total card count, specific words such as `abbrechen` and its conjugation
table). If you intentionally change what ships, update those expectations in
the same change, and say so — a changed card count is a user-visible change,
not an incidental one.

## What needs a human decision

- Adding or removing a deck from `tools/deck_sources.json`.
- Anything touching `card_uid()` — it would reset every user's progress.
- Signing, `applicationId`, `versionCode`, or anything else in the release path.
- Adding a dependency that needs network access or a permission. The app has
  neither today, and that is a feature worth protecting.
